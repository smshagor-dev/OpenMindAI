# OpenMindAI — Live Web Search and Advanced Deep Research

Updated: 2026-10-17

## Features and limits

Web Search and Deep Research remain **local-model-first**. Only retrieval uses
the internet. Search uses configured official APIs when available and public
web search pages otherwise; no paid external AI model is required.

- Web Search: fallback between Brave Search API (optional), legacy Google Custom
  Search JSON API (optional), DuckDuckGo HTML and Bing public search HTML,
  with Bing RSS as a fallback when HTML results cannot be parsed.
- Deep Research: four distinct search questions, up to 12 unique sources,
  and up to eight HTML/text/PDF sources. Ordinary Web Search fetches three sources.
- Each full source receives a maximum of 1.5 MB of transfer and 2,200
  characters of cleaned text in the prompt. This is an *extract*, not a
  complete unlimited article transcript. Search responses are capped at 1 MB.
  Public, **text-based PDFs** can now contribute cited text evidence using
  the already-pinned Rust PDF parser. Parsing occurs on a blocking worker with
  a six-second wait limit, at most eight pages inspected per PDF, and a
  512 KB decompression limit per page. PDF text is reduced to at most
  32,000 characters before passage selection. Encrypted, scanned/image-only,
  malformed, oversized and unextractable PDFs remain snippet-only sources.
  No PDF scripts are run and no external PDF viewer or OCR is invoked.
  When choosing relevant passages from longer pages, the extractor preserves
  decimals such as `87.5%` across sentence boundaries and matches query
  terms at word boundaries (including hyphenated terms such as
  `GPS-denied`) instead of treating substrings as independent matches.
  Selection remains heuristic and may omit supporting passages.
- The engine marks a result as snippet-only when its page cannot be fetched.
  Sources are numbered consistently; the model must cite their real links,
  assess independent corroboration and disclose uncertainty.
- A separate source list with clickable URLs is generated by the Rust host,
  appended to completed replies and persisted in chat history. These are
  actual search-provider results, **not a guarantee that model statements
  are supported by the linked content**. Cancelled replies get no footer.
- The Rust engine compares bounded, successfully retrieved page excerpts using
  five-word shingles. At least 30 distinct shingles and 80% Jaccard overlap
  are required before a later source is labeled a **possible near-duplicate**
  of an earlier numbered source. Both links remain available, but research
  prompts and the trusted citation footer warn against counting their text
  as independent corroboration. Search snippets alone cannot trigger the
  label. Identical passages might also reflect legitimate quotations;
  this is **not** an authorship, plagiarism or factual-verification verdict.
- After a completed web-backed reply, the Rust host checks citation numbers,
  distinguishes pages that were actually retrieved from snippet-only results,
  and compares adjacent cited clauses with the bounded text of each retrieved
  page. If a citation has weak distinctive keyword overlap, it adds a warning
  to review the claim. This is a conservative **lexical review signal**,
  **not semantic entailment, factual verification, or proof of corroboration**.
  The selected page passages stay in the request's memory for this check and
  are not separately persisted to chat history.
- A complementary numerical citation audit compares dates, percentages and
  other explicit numerical values in cited claims with values occurring in
  each corresponding retrieved page excerpt. Comma-grouped numbers and decimal
  variants are normalized; code and citations themselves are ignored. When
  a figure is absent, the app adds a **numerical evidence warning** for
  manual verification against the original article. Missing excerpt values
  may be caused by summarization, formatting or incomplete retrieval, while
  matching values may still be misleading or have different units. This is
  **not** proof of correctness, numerical entailment or contradiction.
- Max elapsed retrieval: 35 seconds (search) and 85 seconds (research),
  per-request deadline 9 seconds, concurrent page fetches at most three.
  The user can cancel search while it is running.
- The chat now receives local `web-research:progress` events from the Rust
  retrieval engine: completed search questions, completed public-page checks,
  successful page reads, discovered sources and the transition to answer
  generation. The UI displays actual counts, not an estimated percentage.
  Progress is attached to its conversation and assistant message and clears
  when generation finishes. This is transient activity, not persisted history.
- Backend privacy preferences are checked before network retrieval. Web
  Search and Deep Research settings are independent. The Capabilities settings
  panel checks connectivity automatically when opened and every 60 seconds,
  with a manual Check connection button. Disable both modes to turn off
  this probe.

## Production search configuration and diagnostics

Open **Settings → Capabilities** to select a preferred provider, save optional
Brave/Google credentials, and inspect the health of each search backend. Keys
are stored through the existing Windows Credential Manager / platform secret
storage implementation and are never returned to JavaScript after saving.
Credential status reports only configured/unconfigured flags. Runtime
environment variables remain supported as a fallback. The selected provider
runs first when configured; others remain available for failover.

Search requests retry only transport failures and HTTP 5xx responses, up to
three total attempts with 250/500 ms backoff delays. HTTP 429 honors a bounded
`Retry-After` delay (5–180 seconds, default 45 seconds) and skips that provider
temporarily. HTTP 401/403 marks it blocked (90 seconds). Other providers
continue without requiring a paid search account. Cancellation interrupts
retries and sleeps.

Health checks send a small **real search query** to each configured backend,
test whether usable results can be parsed, and return independent status
labels: healthy, rate limited, blocked, empty results, invalid response,
unreachable or unconfigured. Status does not guarantee that an arbitrary
future query will succeed. Opening the Capabilities panel runs a probe and
repeats it once a minute while the panel is open. Disable both web capabilities
to suppress these probes.

Full-page enrichment uses direct connections and publicly resolved pinned
addresses; proxy-only networks may retrieve search snippets but will not read
remote pages through an untrusted proxy. This preserves the public-only
destination constraint.

### Local smoke test

1. Enable Web Search and confirm provider health with direct internet access.
2. Search a recent public fact; inspect generated host-side source links.
3. Disable Web Search and Deep Research and confirm the app makes no probe.
4. Remove internet access and confirm local chat still responds without
   claiming live source verification.
5. Configure a valid Brave key, then deliberately invalid credentials; confirm
   fallback to keyless providers and no secrets in logs or chat history.
6. Test a network requiring a manual/system proxy and a blocked provider.
7. Check Stop while retrieval is running, and confirm no citations append to a
   cancelled reply.
8. Fetch a public text-based PDF, a scanned PDF, an encrypted PDF, and a PDF
   served as octet-stream. Confirm only successfully extracted text is marked
   as retrieved evidence and malformed documents never crash the app.

CI covers parsing, retry classification, provider ordering and a local HTTP
429 response fixture. These tests do not prove live vendor availability,
which varies with geography, bot challenges and account eligibility.

## Provider credentials and availability

The following **optional** environment variables are read by the Rust app
process, never committed to GitHub, inserted into prompts, or exposed to
frontend JavaScript:

- `OPENMINDAI_BRAVE_SEARCH_KEY` — Brave Search API token.
- `OPENMINDAI_GOOGLE_CSE_KEY` — existing Google Custom Search JSON API key.
- `OPENMINDAI_GOOGLE_CSE_ID` — associated Programmable Search engine ID.

Brave Search API may require an account/paid plan; never imply it is a free
anonymous provider. Without credentials the app falls back to DuckDuckGo HTML
and Bing HTML search; both are best-effort and may rate-limit, challenge bots,
change page markup or be unavailable in a country. The old Microsoft Bing
Search **API** was retired August 11, 2025; the implementation does not invoke
it. Google Custom Search JSON API is closed to new users and scheduled to
discontinue January 1, 2027. Do not rely on Google as a future default.

Provider and official product details:
- https://api-dashboard.search.brave.com/documentation/guides/authentication
- https://developers.google.com/custom-search/v1/overview
- https://learn.microsoft.com/lifecycle/announcements/bing-search-api-retirement

## Security

A retrieved page is untrusted data, not an instruction to the assistant.
No JavaScript is run. Fetches are limited to HTML, XHTML and plain text.

Before fetching, the application rejects direct private/loopback/link-local
URLs, resolves every hostname and rejects **any** nonpublic returned address.
The approved public IPs are pinned for the request. Redirects are disabled to
avoid crossing into local/private networks via a malicious redirect. Page
response types, sizes, timeouts and cancellation are bounded. Some proxies
resolve hostnames independently, so system proxies should be trusted.

Search query text is sent to external providers only when the corresponding
feature is enabled. API keys should be provided by the deployment environment
or future secret-store UI, not placed in a source-controlled configuration.

## Verification and future enhancements

- Automated unit tests cover JSON results, Bing HTML fixture parsing,
  URL deduplication, text extraction, and private-IP rejection.
- CI validates TypeScript + frontend + Rust on Windows, Linux and macOS.
- Tests do **not** prove live provider success on every user's network:
  complete a live Windows smoke test including offline, proxy, Brave/Google
  credentials, search engine rate limits, and malformed HTML.
- PDF reading supports selected text-based pages only (not complete arbitrary
  research articles, scans, images, tables or math layout); JavaScript-only
  websites are not rendered. Full factual cross-verification cannot be
  guaranteed by an offline 4B model; where claims conflict, the assistant must
  describe both with citations.
- Source snippets might be inaccurate even when returned by a search engine.
  Answer quality should not be overstated as equivalent to ChatGPT's cloud web
  search or the work of professional research fact-checkers.
